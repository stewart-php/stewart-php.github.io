Typed entities

make generate reads your Home Assistant once and writes a PHP class for every domain, entity and service into generated/. Your editor then completes entity IDs, attributes and service fields, and PHPStan checks them:

  • Entities has one property per domain: $this->entities->light, $this->entities->binarySensor.
  • getEntity('light.hall') returns a typed handle. Its methods are that domain’s services: turnOn() takes the light’s real fields, such as brightnessPct and colorTempKelvin.
  • Services has one property per domain, with every service of it: $this->services->notify->mobileAppPhone().
  • LightState::fromNullableState($change->to) turns a state into a typed one, with isOn() and an accessor per attribute, such as getBrightness().

Both classes are ordinary constructor parameters, and calls through them appear in the log under the app’s ID, like calls through HaContext.

Generating

Section titled “Generating”

Run it again after you add devices, and commit generated/. A build or a server then never needs Home Assistant to create the classes.

If Stewart notices at start that Home Assistant has entities the classes do not, it logs one warning:

make generate ARGS=--check reports what would change without writing anything, and fails if something would. When more than half of the files would be deleted, make generate stops, in case it reached the wrong Home Assistant; ARGS=--allow-shrink lets it go ahead.

Entity IDs from options

Section titled “Entity IDs from options”

getEntity() takes a string, so an ID from the app’s options works like one written in the code:

getEntity() accepts only IDs of its domain that the last make generate saw. Any other throws IdentifierException with the reason EntityNotGenerated. Until you generate again, a new entity is still reachable through $this->ha->getEntity('light.new').

Because IDs are written in full, searching your project for light.hall finds every place that uses it.

What gets generated

Section titled “What gets generated”
Class Holds
Entities One property per domain with entities
LightEntities getEntity('light.…') for the domain
LightEntity One entity: getState(), requireState(), watchStateChanges(), waitForState(), getHistory(), and the domain’s services as methods
LightState A typed state: isOn(), isOff(), isUnavailable(), getFriendlyName(), one accessor per attribute, and raw for the plain EntityState
Services One property per domain with services
LightServices Every service of the domain
Manifest What Home Assistant looked like, so Stewart can notice changes
.phpstorm.meta.php Completion of entity, area, floor and label IDs in PhpStorm

A few naming rules:

  • Domains become camelCase properties: binary_sensor is $entities->binarySensor.
  • A service field with a fixed list of values accepts only those, so PHPStan rejects a value Home Assistant would.
  • A service named like an existing method gets a Service suffix, and an attribute named like an existing accessor gets an Attribute suffix.

Choosing what to generate

Section titled “Choosing what to generate”

Everything is optional; these are the defaults:

include and exclude take entity IDs and patterns, such as light.debug_*. Exclude wins.

An attribute gets an accessor when Home Assistant defines it for the domain (such as brightness on a light), or when you include it:

Accessors are nullable, because Home Assistant drops an attribute when it stops applying. Numbers are always ?float, since 21 today can be 21.5 tomorrow. An attribute that was null on every entity when you generated (every light off, for example) is mixed until you generate again.

Snapshots for CI

Section titled “Snapshots for CI”

--snapshot-out saves what generate read, and --snapshot-in generates from that file without connecting. In CI, check the committed classes against a committed snapshot:

Generating from the same snapshot always gives the same files. A snapshot is a copy of your home’s state, with locations, IP addresses and access tokens of cameras, so keep it out of public repositories. The same goes for generated/, which names your entities.

In production

Section titled “In production”

Projects from the skeleton require stewart-php/codegen like any other package, so stewart generate also exists on a server. That is what STEWART_BOOT_GENERATE=1 (or the Helm chart’s code.generateOnStart) uses to regenerate the classes on every start. The generated classes themselves need only stewart-php/contracts; a project that always commits them can move stewart-php/codegen to require-dev.

Common problems

Section titled “Common problems”

Entity ID "…" is not a generated … entity. The ID has a typo, belongs to another domain, or was added after the last make generate.

The first make generate stops and prints a composer.json snippet. Composer does not know where the classes go. Add the snippet under autoload, run make install, then make generate again. Projects from the skeleton already have it.

Class "Stewart\Contracts\App\Generated\…" not found. An app imports Stewart\Contracts\App, so inside the app, App\Generated\Entities means Stewart\Contracts\App\Generated\Entities. Import the generated classes with use App\Generated\Entities; instead.
