Changelog

Every package, the ghcr.io/stewart-php/runtime image, the Helm chart, the skeleton and the Home Assistant integration share one version. The format follows Keep a Changelog, and from 1.0 Stewart follows semantic versioning: only a major release breaks. Before 1.0, a minor release could break; a release’s “Upgrading” section says what to change.

[2.0.0] - 2026-10-24

One word for one thing: Stewart calls Home Assistant’s actions actions everywhere, from callAction() and ActionTarget to the generated Actions classes, the ha_calls settings and the metrics, so “service” means only your own services.php classes. Apps have one way to run code later, the scheduler, and ask HaContext how long an entity has held its state. New projects use the Automations namespace. Everything 1.x deprecated is gone, and a project with 1.x generated classes or settings is told what to run instead of failing to start.

Added

  • stewart check, the deploy gate, stewart run and a reload refuse generated classes written by Stewart 1.x with one line that says to run stewart generate, instead of failing to load them; the PHPStan extension reports such a tree once (stewart.generatedCode) and checks no entity IDs or action names until it is regenerated (#133)
  • HaContext::hasHeldStateFor('binary_sensor.hall_motion', Duration::minutes(10)) and getHeldStateDuration() say how long an entity has held its state, with no clock to pass; an entity that does not exist has held nothing (#137)
  • Scheduler::waitFor($arm, $timeout) builds a wait of your own: $arm starts what resolves it, and the closure it returns cleans up once the wait ends (#136)
  • stewart run --dry-run turns on ha_calls.dry_run for one run, and reloads keep it; make run DRY_RUN=1 uses it (#134)

Changed

  • Stewart\Contracts\Service is now Stewart\Contracts\Action, so the types for calling an action carry its name: ActionTarget, ActionTargetSource and ActionResponse, with toActionTarget(). ServiceCallException and ServiceCallError are ActionCallException and ActionCallError, with the same reasons; their messages and context name the action. ActionResponse::$action and the testing package’s RecordedActionCall::$action replace $service (#130)
  • The generated root is Actions, and each domain’s class is <Domain>Actions (LightActions), so apps write $this->actions->notify->mobileAppPhone(). A generated member that clashes with another takes an Action suffix instead of Service. The generated Manifest implements Stewart\Contracts\Generated\Manifest, which now lists the action names itself (#132)
  • The generated format is 11, so stewart status and the start log ask for stewart generate until the classes are regenerated (#130), (#132), (#137)
  • stewart generate refuses only a run that would leave fewer than half as many generated files as before, so renamed classes no longer need --allow-shrink; its summary counts actions (#132)
  • service_calls is now ha_calls (STEWART_HA_CALLS__*), since its limits and dry run also cover event fires and registry edits. An old service_calls key or STEWART_SERVICE_CALLS__* variable stops the start with the new name. Dry-run log lines name ha_calls.dry_run, and an action says Action call not sent (#134)
  • Metrics and status name what they count, every call to Home Assistant: stewart_app_service_calls_total, stewart_app_service_call_duration_seconds, stewart_service_calls_in_flight, stewart_service_calls_refused_total and stewart_worker_service_calls_in_flight are now stewart_app_ha_calls_total, stewart_app_ha_call_duration_seconds, stewart_ha_calls_in_flight, stewart_ha_calls_refused_total and stewart_worker_ha_calls_in_flight. In the status JSON, in_flight_service_calls, refused_service_calls and service_calls are in_flight_ha_calls, refused_ha_calls and ha_calls, and stewart status shows an HA calls row (#135)
  • Trace lines say Action call sent and Action call answered, with the name under action (#135)
  • codegen.namespace is optional and defaults to the namespace composer.json maps to codegen.output_dir, which is App\Generated in projects created before 2.0, so they need no setting; stewart-php/phpstan finds the generated Manifest the same way, and stewart.manifest is needed only when several namespaces map the directory (#138)
  • New projects use the namespace Automations (Automations\Generated, Automations\Tests) instead of App, which clashed with the Stewart\Contracts\App interface every app imports. Existing projects keep App and need no change, and the docs examples use the new namespace (#139)
  • The worker protocol is 35 and the control protocol 34, so make status and the other control targets refuse to talk to a daemon that still runs 1.x (#130), (#135)

Removed

  • HaContext::callService() and callServiceForResponse(), the same on Entity, and in tests RecordingHaContext::stubServiceAnswer(), stubServiceFailure() and RecordedServiceCall::getServiceName(), all deprecated since 1.8: use callAction(), callActionForResponse(), stubActionAnswer(), stubActionFailure() and getActionName() (#126)
  • Stewart no longer calls a public dispose() on an app that does not implement Disposable, deprecated since 1.5, and stewart check no longer names such apps (#128)
  • GET /metrics on the admin port: only the metrics port (http.metrics.listen) serves metrics, and the admin port answers 404 with a pointer to it (#129)
  • Stewart\Contracts\Time\Timers and TimerHandle, so apps have one way to run code later: Scheduler::runAfter(), which shows in status and in traces. In tests, AppHarness::$timers and RecordingHaContext::$timers are private; use advanceTime(), or give RecordingHaContext a ManualTimers of your own and advance that (#136)
  • EntityState::hasHeldFor($duration, $clock) and getHeldDuration($clock): use HaContext::hasHeldStateFor() and getHeldStateDuration() (#137)
  • Stewart\Contracts\Generated\ActionManifest: its listActionNames() is part of Manifest (#132)
  • Chart: adminApi.podMonitor, deprecated since 1.8; a release that still sets it fails to render and names metrics.podMonitor (#129)

Upgrading

  1. Run make upgrade VERSION=2.0. It requires 2.0 and moves the image tags to runtime:2 (runtime:2-dev in compose.dev.yaml). Do the steps below before you deploy: the control protocol is now 34, so make status and the other control targets refuse to talk to a daemon that still runs 1.x. The Home Assistant integration’s protocol is unchanged; update it to 2.0.0 with the rest.

  2. From make sh, rewrite the names that 2.0 changed in your apps, tests, services.php and settings. The commands rewrite the names they recognise; make stan then points at the rest, such as names held in a variable:

    The second command renames the generated Services and <Domain>Services in files that import generated classes, and a class of yours whose name ends in Services there too. It leaves ->service on an ActionResponse or a RecordedActionCall alone, which is ->action now, and a call to a generated method with a Service suffix, which has an Action suffix now. The third renames service_calls in stewart.yaml and its variables in .env and the Makefile; on Kubernetes, rename them in the chart’s config and env values by hand.

  3. Run make generate and commit generated/: Stewart 2.0 refuses the classes 1.x generated.

  4. An app whose dispose() does something implements Stewart\Contracts\Disposable, or it no longer runs. Before upgrading, stewart check on 1.8 names every app this affects.

  5. An app that took Timers takes Scheduler instead: startTimer($delay, $callback) becomes runAfter($delay, $callback), isPending() on the handle becomes isActive(), and waitFor() moves to the Scheduler unchanged. $state->hasHeldFor($duration, $this->clock) becomes $this->ha->hasHeldStateFor($state->entityId, $duration). make stan points at each one.

  6. If Prometheus scrapes the admin port, turn on the metrics port and scrape that: http.metrics.listen (STEWART_HTTP__METRICS__LISTEN, port 9464 by convention) with Docker, or metrics.enabled and metrics.podMonitor.enabled instead of adminApi.podMonitor with the chart. If Prometheus was the only reason for adminApi.host: 0.0.0.0, set it back to 127.0.0.1.

  7. Rename the metrics in dashboards and alerts, and the status JSON keys in scripts that read stewart status --json; both lists are under Changed.

  8. On Kubernetes, upgrade the chart to 2.0.0 in the same deploy, after moving any adminApi.podMonitor values and any service_calls under config or STEWART_SERVICE_CALLS__* under env.

[1.8.0] - 2026-10-23

Fewer copies, fewer typos: call actions by the names Home Assistant gives them, run one app class several times with its own settings, and let PhpStorm and PHPStan catch a mistyped entity ID or action name before it reaches Home Assistant. Prometheus gets a port of its own, so it no longer holds the token that can pause apps.

Added

  • HaContext::callAction('light.turn_on', $data, $target) and callActionForResponse() call a Home Assistant action by the name Home Assistant gives it; Entity::callAction('turn_on') calls one of the entity’s own domain. A name without exactly one dot throws ServiceCallError::ActionNameInvalid before anything is sent. In tests, RecordingHaContext::stubActionAnswer('weather.get_forecasts', …) and stubActionFailure() stub actions by the same name, and recorded calls answer getActionName() (#118)
  • EntityState::isOn() and isOff() read raw states as the typed state classes already do (#118)
  • apps.<id>.class runs a class once more under that ID, with the entry’s own options and settings, so one class can serve several rooms. A class marked #[AppTemplate] instead of #[Automation] runs only through such entries, and the class may come from a Composer package. A reload applies added and removed entries; a mistyped class names the closest one, and stewart check notes a template that no entry names. AppHarness::startApp(…, appId: 'hall-light') runs an app under the ID of one entry, which an #[AppTemplate] needs (#120)
  • stewart make:app PorchLight --template (make app NAME=… TEMPLATE=1 in new projects) writes an #[AppTemplate] class and a test for one entry, and prints the stewart.yaml entry that runs it; make:app also refuses an ID that a class entry already uses (#121)
  • The test harness matches option names as Stewart does: motion_sensor reaches $motionSensor, a misspelled option names the closest parameter, and two options for one parameter are refused (#121)
  • stewart check lists the apps by class, so the entries that run one class sit together, and shows a template that no entry names (#121)
  • .phpstorm.meta.php completes entity IDs wherever a method takes one (HaContext, ServiceTarget::forEntities(), Scheduler::runAtEntityTime(), HaTrigger, Registry, EntityId), zones for onZoneTransition(), and action names for callAction(). The generated Manifest lists the action names too, through the new Stewart\Contracts\Generated\ActionManifest (#122)
  • stewart-php/phpstan, a PHPStan extension, checks literal entity IDs and action names against the generated Manifest: a typo fails make stan with the closest known name, and a generated getEntity() for an entity left out of codegen is reported, since it throws at run time. Its errors use the identifiers stewart.entityId and stewart.actionName. New projects from the skeleton have it (#123)
  • http.metrics.listen (STEWART_HTTP__METRICS__LISTEN) serves only GET /metrics, on a port of its own, so Prometheus no longer needs the admin token that can pause apps. http.metrics.token is optional: without one, anyone who reaches the port reads the metrics. /metrics on the admin port keeps working under the admin token (#116)
  • stewart check notes, and stewart doctor and a reload refuse, an admin port without a token and two HTTP ports on one port, which before showed only when the daemon refused to start (#116)
  • Chart: metrics.enabled opens the metrics port (9464) with a token the chart generates, or one from metrics.existingSecret, and metrics.podMonitor scrapes it, so the admin API can stay on loopback (#117)
  • Chart: networkPolicy.enabled creates ingress NetworkPolicies. The probe port stays open, the metrics and admin ports admit only networkPolicy.metrics.from and networkPolicy.adminApi.from, and Valkey admits only Stewart (#117)

Changed

  • Generated services and entity methods call callAction(). The generated format is 8, so stewart status and the start log ask for stewart generate until the classes are regenerated (#118), (#122)
  • The guide “Calling services” is now “Call actions”, at guides/calling-actions/; the old address redirects to it. The scheduling guide says when to use a schedule and when a timer (#118)
  • The admin API logs a warning when it listens off loopback, as the control socket already does (#116)
  • A request refused for a missing or wrong token on the admin or metrics port logs a warning: the first, then every 100th (#116)
  • Chart: helm upgrade rolls the pod when a Secret named in an existingSecret has changed, since Stewart reads secrets only at start (#117)

Deprecated

  • HaContext::callService() and callServiceForResponse(), and the same on Entity: use callAction() and callActionForResponse(). In tests, stubServiceAnswer(), stubServiceFailure() and RecordedServiceCall::getServiceName(): use stubActionAnswer(), stubActionFailure() and getActionName(). They keep working, each call prints a PHP deprecation line, and 2.0 removes them (#119)
  • Chart: adminApi.podMonitor, which scrapes with the admin token; use metrics.podMonitor. It is removed in 2.0 (#117)

Upgrading

  1. Run make upgrade VERSION=1.8, then restart Stewart (make up, make deploy or a new image). The control and worker protocols are unchanged, and so is the Home Assistant integration’s.

  2. Run make generate. The generated classes of 1.7 and earlier call callService(), so until they are regenerated every generated call prints a deprecation line in the log, and make status says the classes are of an older format.

  3. Move your apps and tests to the action names. This rewrites the calls whose names are written out; make stan then points at the rest, such as names held in a variable:

  4. To have make stan check entity IDs and action names, add the PHPStan extension from make sh; new projects from the skeleton have it:

  5. On Kubernetes with adminApi.podMonitor.enabled, switch to metrics.enabled: true and metrics.podMonitor.enabled: true, and turn adminApi.podMonitor off. If Prometheus was the only reason for adminApi.host: 0.0.0.0, set it back to 127.0.0.1.

  6. The TEMPLATE variable of make app reaches only new projects. To use it, copy the app target from the skeleton’s Makefile.

[1.7.0] - 2026-10-22

Find out why an automation fired or did not: per-app log levels and traces, and a status that shows when each subscription last fired and when each schedule runs next.

Added

  • apps.<id>.log_level (STEWART_APPS__<ID>__LOG_LEVEL) gives one app a log level of its own, louder or quieter than log_level; a reload applies it. A new Logs guide explains the log line (#108)
  • apps.<id>.trace and stewart run --trace=<id> (make run TRACE=…, also watch and debug) log TRACE lines for one app at any log level: each event that reaches one of its subscriptions, each call of its handler, what a pause skipped, its schedule runs, and its service calls with the outcome and how long they took. An event received but never handled was stopped by an operator such as filter(). In JSON logs, trace records have level_name TRACE (#109)
  • stewart status --json lists every subscription, now including state changes, with how many events it received and handled, how many it dropped, and when it last received and handled one; and every schedule and timer with its next and last run. Each app gains last_handled_at, next_run_at and counters.handled, also in the admin API’s GET /api/apps, and stewart_app_events_handled_total, stewart_app_last_handled_timestamp_seconds and stewart_app_next_run_timestamp_seconds expose them (#110)
  • stewart status <app>… (make status APP=…) shows only those apps, and adds a Subscriptions table (received, handled, dropped, last handled) and a Schedules table (next and last run); an unknown ID names the closest one, and --json narrows the same way. --watch[=2s] (make status WATCH=1) redraws until Ctrl-C and keeps trying while Stewart is down. The Apps table shows last handled and next run (#111)
  • stewart status shows the MQTT connection on an mqtt row: its phase and since when, reconnects, the last outage and error, QoS 1 messages waiting and messages dropped. stewart_mqtt_connection_phase{phase}, stewart_mqtt_reconnects_total, stewart_mqtt_messages_dropped_total{reason} and stewart_mqtt_outbound_queued expose the same (#112)
  • stewart status shows on a generated row whether the generated classes still match Home Assistant: up to date, how many entities were added or removed since stewart generate, or an older format. stewart_generated_entities_drift{change} and stewart_generated_format_current expose the same (#113)

Changed

  • Every log line names what it is about after the level: the app ID, @shared for Stewart’s code inside a worker, broker, or worker N for text a worker printed outside the logger. Lines Stewart writes about an app, such as App failed or App paused, carry that app’s tag and follow its log level, and the line no longer repeats the app ID in its trailing details. JSON logs keep context.app and add the tag as extra.source (#108)
  • The broker’s routing debug lines (Home Assistant event routed, Topic published, MQTT message routed, Home Assistant trigger routed) name the matched apps instead of worker numbers, and the service_calls.dry_run lines carry the tag of the app that made the call (#109)
  • Warnings about dropped MQTT messages come for the first drop of each kind and then every 100th, with the count so far, instead of one per message (#112)
  • Generated classes are compared with Home Assistant again after each reconnect, after entities are added or removed, and after each reload, which compares against the classes stewart generate wrote last. The warning repeats only when the difference changes, and an info line notes when the classes match again (#113)
  • The control protocol is 33, so stewart status and the other control commands need the same release as the daemon (#110, #112, #113)

Security

  • Every package and the skeleton require PHP 8.5.12, the security release that fixes the Core advisories GHSA-w8hw-w9fx-j79w and GHSA-6wmf-4rv5-p3rp. The runtime images published since 2026-10-21, including 1.6.0, already run it; a project that runs Stewart outside the image needs PHP 8.5.12 before composer install accepts it. make build and make image now always pull the latest PHP 8.5 base image (#114)

Upgrading

  1. Run make upgrade VERSION=1.7, then restart Stewart (make up, make deploy or a new image). The control protocol is now 33: until the daemon runs 1.7, make status and the other control targets refuse to talk to it. The Home Assistant integration’s protocol is unchanged.
  2. Stewart 1.7 needs PHP 8.5.12. The runtime image already runs it, so make pull is enough; a project that runs Stewart outside the image updates PHP first.
  3. Log lines name their source after the level, such as INFO [porch-light] …. Anything that parses line logs needs to allow for the tag; JSON logs only gain extra.source.
  4. The new Makefile variables reach only new projects. To use them, copy TRACE on run, watch and debug, and APP and WATCH on status, from the skeleton’s Makefile.

[1.6.0] - 2026-10-21

Edit apps and their settings without restarting: a reload restarts the workers on the current code and app settings while the Home Assistant session stays open, and make watch reloads on every save.

Added

  • stewart reload (make reload), POST /api/reload and SIGHUP check the project as stewart check does, then restart every worker on the current code while the Home Assistant session stays open; a failed check leaves everything running. These restarts do not count toward a worker’s restarts, and a quarantined worker comes back. stewart status shows the last reload on a reload row, and stewart_reloads_total{outcome} counts them (#103)
  • A reload also applies stewart.yaml and the app list: added and removed apps, apps.<id> options, enabled, paused and worker, and workers. Any other changed setting keeps its value until a restart, and the reload row says partly applied and names it (#104)
  • stewart run --watch (make watch in new projects) reloads once a saved change to the apps, services.php or stewart.yaml settles; a changed .env or composer.lock is logged as needing a restart (#105)

Changed

  • In Git mode, the image entrypoint forwards SIGHUP to the daemon; before, it stopped the container (#103)
  • The control protocol is 30, so stewart status and the other control commands need the same release as the daemon (#103)
  • After a reload removes an app, its exposed entities are deleted after the usual grace when expose.prune is on (#104)

Upgrading

  1. Run make upgrade VERSION=1.6, then restart Stewart (make up, make deploy or a new image). The control protocol is now 30: until the daemon runs 1.6, make status and the other control targets refuse to talk to it. The Home Assistant integration’s protocol is unchanged.
  2. The new targets reach only new projects. To use them, copy reload and watch from the skeleton’s Makefile.
  3. docker compose kill -s HUP stewart now reloads Stewart instead of stopping it, also in Git mode.

[1.5.0] - 2026-10-21

Mistakes surface before they reach the server: stewart check builds every app, and new projects run it in CI and before every make deploy.

Added

  • stewart check builds every enabled app’s container the way its worker does, without running any app code, and fails naming each app that cannot be built: a missing or unknown option, a constructor argument nothing provides, a Store without persistence.url, an Mqtt without mqtt.url, or a #[PeerStore] naming no app, with the closest ID (#96)
  • stewart check notes classes in apps/ that implement App without #[Automation], as stewart run does (#96)
  • Stewart\Contracts\Disposable for apps that release something when they stop; apps that open nothing need no dispose() any more, and new projects, make:app and the examples have none (#99)
  • The test harness’s recorded handles send commands without building them: pushTurnOn() and pushTurnOff() on a switch, pushPress() on a button, pushOption() on a select, and pushValue() on a number, text, time, date or date-time; the event context defaults to EventContext::unknown() (#100)

Changed

  • A Git deploy rejects a commit with an app that cannot be built, because stewart check now builds the apps; before, the commit went out and that app failed on its own (#96)
  • An app that takes a Store or Mqtt that is not configured, or a #[PeerStore] naming no app, fails when its worker builds the container, with the reason app_build_failed, instead of when it is constructed (#96)
  • New projects’ CI also runs make check against the settings in .env.example, and the Image workflow runs CI first, so a commit that fails it gets no image (#97)
  • make deploy in new projects installs changed dependencies and runs stewart check in one-off containers before it restarts Stewart, so a deploy is down only for the restart, and a failed check leaves the running daemon up (#98)
  • App declares only initialize(); dispose() moved to Disposable. An app that marks dispose() with #[\Override] must implement Disposable, or PHP refuses to load it (#99)
  • An app without worker: is placed by a hash of its ID instead of round-robin, so adding or removing an app moves no other. After the upgrade, apps and their worker metric label move once; the spread can be less even with few apps, and apps.<id>.worker still pins one (#101)

Deprecated

  • A public dispose() on an app that does not implement Disposable. Stewart still calls it until 2.0, and stewart check names each such app (#99)

Upgrading

  • stewart-php/sun: sunrise, sunset, solar noon, twilights, golden and blue hour, and sun position, computed locally with the NOAA equations and Astral’s refraction, so times agree with Home Assistant’s sun integration
    • SunCalendar contract: findNextEvent() with an optional SunOffset, getDayOn(), getPositionAt(), getCurrentPosition(), isSunUp()
    • SunEvent, SunDay, GeoLocation; SunOffset::applyTo()
    • SunPosition with isHigherThan() and isWithinAzimuth(), a sector that may wrap past north
    • Apps get a SunCalendar by type, located at Home Assistant’s latitude, longitude and elevation as read at startup; without a location every query throws SunException (LocationUnknown)
  • Scheduler::runAtSunrise(), runAtSunset() and runAtSunEvent() with an optional SunOffset: a recurring ScheduledTask with getNextRunAt() and missed-run counts; without a location they throw ScheduleException (SunLocationUnknown)
  • HaContext::watchTrigger() streams Home Assistant triggers (subscribe_trigger) as TriggerEvents: sun, time, time pattern, template, zone, calendar, device and any other trigger platform
    • HaTrigger builders: onSunrise(), onSunset() with a SunOffset, atTime(), onTimePattern(), whenTemplateTrue(), onZoneTransition(); HaTrigger::fromArray() takes any trigger config
    • An HaTriggerCollection or a list of configs fires on any of them; variables feed template triggers
    • Apps watching the same trigger share one Home Assistant subscription, re-issued after every reconnect
    • A trigger Home Assistant rejects is logged and its subscription ends (isActive() is false)
  • RecordingHaContext::pushTrigger() and listWatchedTriggers()
  • Duration::formatAsClock()
  • callService() on HaContext, Entity and generated classes returns the call’s EventContext; ServiceResponse::$context carries it for callServiceForResponse()
    • StateChange::wasCausedBy($context) and EntityState::wasLastChangedBy($context) match the call or anything it started (its child contexts)
    • StewartIdentity, injectable in apps, answers wasCausedByStewart($change) from the token’s Home Assistant user; it also recognises the first change of a call, which arrives before callService() returns. It needs a Home Assistant user for Stewart alone: with a token from a person’s account, that person’s changes count as Stewart’s
    • Under service_calls.dry_run the context id starts with dry-run:
  • RecordingHaContext gives each call a context for RecordingHaContext::STEWART_USER_ID, records it on RecordedServiceCall::$context, and pushState() takes a causing context
  • HaContext::fireEvent() fires an event on Home Assistant’s bus and returns its EventContext
    • Event data must be keyed and transportable; nulls are kept; bad input throws EventFireException before sending
    • Fired events share the service_calls in-flight limits, per-app call counts and dry_run with service calls
    • Needs an administrator token, like the rest of Stewart
    • StewartIdentity::wasCausedByStewart() also takes an HaEvent, so watchers can skip Stewart’s own fired events
  • RecordingHaContext::fireEvent() records to firedEvents, echoes the event to watchEvents(), and stubEventFireFailure() makes it throw
  • HaContext::getRegistry() reads Home Assistant’s areas, floors, labels, devices and registered entities
    • findArea(), findAreaByName() (name or alias), listAreasOnFloor(), listDevicesInArea(), findEntityPlacement() and the same lookups for floors, labels, devices and entities
    • Typed AreaId, FloorId, LabelId and DeviceId; every lookup also takes a plain string
    • The broker fetches the registries on every connect and again a second after a *_registry_updated event
  • EntityFilter selects entities by area, floor, label, device, domain or id pattern for listStates() and watchStateChanges(): EntityFilter::inArea('kitchen')->withDomain('light')->withLabel('night')
    • Values within one condition are alternatives; all conditions must match
    • Area, floor and labels resolve like Home Assistant targets: an entity’s own area overrides its device’s, labels come from the entity, its device and its area, and hidden or config/diagnostic entities match only by domain or id
    • A running watch picks up registry changes with the next state change
  • ServiceTarget::forAreas(), forFloors(), forLabels() and forDevices() take the typed ids
  • RecordingHaContext::$registry (InMemoryRegistry) seeds areas, floors, labels, devices and entities for tests
  • stewart generate stores areas, floors and labels in the snapshot and completes their ids in PhpStorm for EntityFilter, Registry lookups, ServiceTarget and the id constructors

Changed

Upgrading

To make life easier in long term, I added an upgrade script, that script needs to be added manually, later on upgrades can be made by executing only one make target.

  1. Fetch the upgrade script and keep it out of the production image:

  2. Add the target to your Makefile, next to update; the recipe lines start with a tab:

  3. To use MQTT, add "stewart-php/mqtt": "^0.2" to require in composer.json.

  4. Upgrade. This points every stewart-php/* requirement and runtime image tag at 0.2, pulls the images and installs:

  5. If you added MQTT, set STEWART_MQTT__URL in .env, such as mqtt://user:password@homeassistant.local:1883, and check the mqtt section with make config. Without the URL nothing changes.
